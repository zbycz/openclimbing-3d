# openclimbing-3d — notes for whoever works on this next

Two reconstructions of the Korno rock face from 103 drone photos (8000 × 4500), plus climbing
metadata projected onto them. [`CONVERSATION.md`](CONVERSATION.md) is how it got here;
[`v2/README.md`](v2/README.md) has the pipeline detail.

```
index.html            v1 splat viewer (Pages root)
kaggle/splat|mesh/    v1: 3DGS on a P100, then splat -> glTF
v2/index.html         the viewer that is actually maintained
v2/kaggle/            dense MVS (GPU) + probe
v2/kaggle/bolts|bolts3d|routes|texture/    CPU kernels for the metadata and the re-bake
```

**The model to serve is `korno_v2_desmudged.glb`** — 90 MB, 2 531 404 triangles, 8192 × 4500 texture
baked from the photos. It is the viewer's default. `korno_v2.glb` (same geometry, the old
point-cloud bake) stays in the repo only for the `texture:` switch; `*_light.glb` are the 12 MB
versions.

## Working rules

- **Everything heavy runs on Kaggle.** This container is small and shares the box with production.
  Minutes-scale work — training, meshing, decimating, baking, bulk inference — goes to a kernel.
  Cheap local checks *save* kernel runs: file headers, API parameter names, `ldd`, small renders.
- **Notebooks are generated by `build_notebook.py`.** Never hand-edit an `.ipynb`.
  `python3 <dir>/build_notebook.py && kaggle kernels push -p <dir>`.
- **Split kernels by what you might re-tune** — bolt inference (23 min) and bolt projection (4 min)
  are separate so the projection can be redone alone.
- **Follow logs in the background**, never with `sleep`:
  `kaggle kernels logs pavelzbytovsk/<kernel> --follow > log 2>&1 &`. Put it in a script file —
  `pkill -f "kernels logs"` matches the shell's own command line and kills the shell.
- **Push to `main`**; Pages serves from it. Commits: `component: short thing in english`, one per
  part of a request. The Kaggle token lives in `~/.kaggle/access_token`, outside the repo.

## Traps that cost a run

- **Kaggle's stock PyTorch has no Pascal kernels** (`sm_70`+, the P100 is `sm_60`). Probe
  `nvidia-smi --query-gpu=compute_cap` *before importing torch*, then install
  `torch==2.6.0 torchvision==0.21.0 --index-url https://download.pytorch.org/whl/cu124`.
- Dataset mount paths move — glob recursively under `/kaggle/input`. `kernel_sources` pulls another
  kernel's outputs in, which beats recomputing intermediates.
- **COLMAP** comes from conda-forge via micromamba (`patch_match_stereo` is CUDA-only, no pip
  wheel). The working spec is `colmap=4.1.1=cuda*` + `libfaiss=1.10.0=*openblas*` + `openimageio`:
  it links faiss and OpenImageIO without declaring them, needs faiss 1.10's ABI, and the solver
  otherwise picks the MKL variant. COLMAP 4.x renamed the option namespaces —
  `--FeatureExtraction.use_gpu`, not `--SiftExtraction.use_gpu`.
- COLMAP's bundled **PoissonRecon segfaults (exit 139) after writing a complete mesh**. Tolerate the
  exit code; validate the PLY byte size against the counts in its own header.
- **trimesh's glTF exporter re-encodes JPEG at quality 75 / 4:2:0** despite a comment saying it does
  not. Monkey-patch `Image.Image.save` to force quality 95, subsampling 0. It also embeds PNG unless
  handed a JPEG round-tripped through `BytesIO`, and omits normals without `include_normals=True`.
- **GitHub rejects files over 100 MiB and Pages does not resolve LFS**, so models are fitted to a
  92 MiB budget. An oversized blob survives in local history — `git reset --soft origin/main` first.
- `pycolmap`: `Camera.rescale(W, H)` scales `f`, `cx`, `cy` and leaves the radial term (normalised),
  so a 3200-px SfM camera maps onto the 8000-px original as a clean 2.5×. Build the copy at the
  *original* size and then rescale — constructing it at the target size makes `rescale` a no-op.
  `img_from_cam` takes camera-frame `(m, 3)` points and returns NaN behind the camera.

## The viewer (`v2/index.html`)

- **Camera framing must account for aspect ratio**: `1.12 * max(size.y/2/halfV, size.x/2/(aspect*halfV))`.
  Distance from `max(size.x, size.y)` alone leaves the model tiny in a wide window. Got wrong twice.
- The world is **y-down** (`camera.up.set(0, -1, 0)`), so the largest `y` is the foot of a route.
- `LineBasicMaterial.linewidth` is ignored in WebGL almost everywhere — use `Line2` + `LineGeometry`
  + `LineMaterial`, and update `resolution` on resize.
- **Two coincident fat lines z-fight** and chop the coloured line into dashes. `polygonOffset` is not
  a fix; the depth error grows as you zoom in. Scale the outline group about the camera each frame
  (`scale = 1+eps`, `position = -camera.position * eps`) so every point moves straight away from the
  eye: screen position unchanged, real distance between the strokes. Cap `eps * distance` below the
  clearance the line was lifted by.
- Pages **gzips the GLB**, so `ProgressEvent.total` is compressed while `loaded` is not and the bar
  overshoots. Hardcode the real sizes.
- Labels are a 2D canvas overlay, not sprites, so boxes can be measured against each other. Keep the
  overlay `pointer-events: none` and hit-test clicks against last frame's boxes, with a "pointer
  barely moved" guard — otherwise every orbit ending on a label navigates away.

## Metadata, not models

Bolts and routes are separate JSON the viewer overlays; the GLBs are never edited.

- **Multi-view agreement beats any confidence threshold.** The bolt detector is out of its training
  domain on drone frames (12–34 px bolts, median score 0.30). Keep every detection, ray-cast it,
  cluster in 3D, and ask whether several photos put a bolt in the same place: 94 of 113 candidates
  were single-view and dropped; the 19 survivors agree to 0.001–0.028 across up to 7 views.
- openclimbing paths are `x,y|x,y|…` normalised to the photo. A **trailing letter on `y` is the
  point type** (`A` anchor, `B` bolt, `P` piton, `S` sling, `U` unfinished) and a trailing colon
  means the segment is dotted. Reading them as plain floats fails.
- Grades are keyed on UIAA in openclimbing's `gradeColors`. The ramp is flat within a tier, so
  `parseInt` on the leading number reproduces the whole table — verified against 14 grades.
- A route drawn with 2–6 points must be **resampled before ray-casting**: the points land correctly,
  it is the chords between them that cut through bulges (up to 94 cm here). Resample, lift along the
  mesh normal, verify by casting back from the camera, then simplify with a tolerance *below* the
  lift so the remaining chords cannot eat through it.

## Why the texture was smudged, and what fixed it

The bake took each texel's colour from the **dense point cloud** (inverse-distance blend of the six
nearest points), so detail was capped by point density — 0.0029 units between points below
h ≈ 1.55 against a 0.00184 texel, but 0.011 above it, because the drone never flew above the top of
the wall. The hard "edge" along the wall is the boundary of what `stereo_fusion --min_num_pixels 4`
accepted: a data boundary, not geometry.

Fixed in `v2/kaggle/texture/` (31 min, CPU): same mesh, same planar UV frame, only the bake replaced.
Each texel is ray-cast to its surface point, projected into all 102 posed photos, filtered for
occlusion against a per-photo depth map, scored by sampling density (`cos / d²`) and sampled from the
original 8000 × 4500 pixels. Local contrast went **4.82 → 35.48 (7.4×)**.

- **The old bake was softening the whole wall, not just the top** — 9–20× gain in the upper bands but
  still 4–7× at the foot. Blending six neighbours is a blur even when they are dense. The old bake's
  contrast falls monotonically with height (8.2 → 1.2); the new one is flat (44 → 11). That band
  structure *was* the defect.
- **97.9 % of surface texels are seen by ≥ 1 photo.** Coverage was never the problem.
- **Do not go shopping for a texturing package** — conda-forge has no `openmvs`, no `mvs-texturing`.
  A per-texel bake is ~200 lines of numpy + Open3D on what this repo already installs.
- **A planar UV atlas makes the position map trivial**: `to_uv` drops the view-axis component, so a
  texel *is* a line through the scene — one ray-cast each, 36.9 M in 15 s, no rasteriser. Occlusion
  is a lookup in a 1024 px depth map per photo (102 maps in 21 s), not a second ray.
- **Blend narrowly**: `w = (s / s_best)^8` over the best three is the single best view almost
  everywhere and a thin cross-fade only where two are equal, so misregistration never blurs.
- **Fit exposure gains against the old bake** — it averages every view that saw a point, so it is a
  stable anchor. `img.draft("RGB", …)` decodes at 1/8 scale, so this costs 29 s. Gains 1.02–1.05
  mean, 20 of 102 photos clipped at ±18 %, no seams visible at zoom.
- **A sharper texture is a bigger JPEG**: 9.9 → 22.1 MiB, so the triangle budget for 92 MiB dropped
  3.0 M → 2.53 M. Detail moved from geometry to texture, which on this wall is the better trade.

Still open, and not fixable from the bake: the planar UV **stretches on faces > 45° off the wall
plane** (17 % of triangles; a real unwrap would spend the budget evenly), and the **geometry above
h ≈ 1.85 rests on very few depth measurements** — only a flight that looks at the top fixes that.
