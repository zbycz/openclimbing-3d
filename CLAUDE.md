# openclimbing-3d — notes for whoever works on this next

Two independent reconstructions of the Korno rock face from the same 103 drone photos
(8000 × 4500), plus climbing metadata projected onto them. See [`CONVERSATION.md`](CONVERSATION.md)
for how it got here.

```
index.html            v1 splat viewer (GitHub Pages root)
kaggle/splat/         3DGS on a P100
kaggle/mesh/          splat -> textured glTF, CPU
v2/index.html         v2 viewer - the one that is actually maintained
v2/kaggle/            dense MVS (GPU) + probe
v2/kaggle/bolts/      YOLO ONNX inference, CPU
v2/kaggle/bolts3d/    detections -> 3D, CPU
v2/kaggle/routes/     openclimbing route paths -> 3D, CPU
```

## Working rules

- **Everything heavy runs on Kaggle.** This container is small and shares the box with production.
  Anything measured in minutes — training, meshing, decimating millions of triangles, baking
  textures, bulk inference — goes to a kernel. Cheap things *should* be done locally, because they
  save whole kernel runs: reading file headers, checking an API's parameter names, `ldd` on a
  library, small control renders.
- **Every notebook is generated by its `build_notebook.py`** so the source stays diffable. Never
  hand-edit an `.ipynb`. `python3 <dir>/build_notebook.py && kaggle kernels push -p <dir>`.
- **Split kernels by what you might want to re-tune.** Bolt inference (23 min) and bolt projection
  (4 min) are separate so the projection can be re-run without repeating the inference.
- **Follow logs in the background**, never with `sleep`:
  `kaggle kernels logs pavelzbytovsk/<kernel> --follow > log 2>&1 &`. Put the command in a script
  file — `pkill -f "kernels logs"` matches the shell's own command line and kills the shell.
- **Push to `main`.** Pages serves from it, so nothing is done until it is pushed.
- Commit messages: `component: short thing in english`. Commit per part of a request, not at the end.
- The Kaggle token lives in `~/.kaggle/access_token`, outside the repo. Keep it that way.

## Kaggle

- The P100 is `sm_60` and **Kaggle's stock PyTorch has no Pascal kernels** (`sm_70`–`sm_120`).
  Probe `nvidia-smi --query-gpu=compute_cap` *before importing torch* and, on 6.0, install
  `torch==2.6.0 torchvision==0.21.0 --index-url https://download.pytorch.org/whl/cu124`.
- Dataset mount paths move. Glob recursively under `/kaggle/input` instead of hardcoding.
- `kernel_sources` pulls another kernel's outputs in — cheaper than recomputing intermediates here.
- The proxy this container shares gets 429s from Wikimedia. Download such assets inside the kernel.

## COLMAP (v2)

- `patch_match_stereo` is CUDA-only, no CPU fallback and no pip wheel → conda-forge via micromamba.
  The working spec is `colmap=4.1.1=cuda*` + `libfaiss=1.10.0=*openblas*` + `openimageio`:
  colmap links faiss and OpenImageIO without declaring them, is built against faiss 1.10 (1.14 has
  a different ABI), and the solver otherwise picks faiss's MKL variant.
- COLMAP 4.x renamed the option namespaces — `--FeatureExtraction.use_gpu`, not
  `--SiftExtraction.use_gpu`. Validate flag sets locally with a dry parse before spending a run.
- Its bundled **PoissonRecon segfaults (exit 139) at depth 13 — after writing a complete mesh**.
  Tolerate the exit code and validate the PLY by comparing its byte size against the vertex and
  face counts in its own header.
- Cost model from the probe kernel: `patch_match_stereo` ≈ 15.5 s/image at 1200 px on a P100, and
  scales with pixels × source views. That is how the 2 h 21 m run was sized before committing to it.

## Meshes and glTF

- trimesh's glTF exporter **re-encodes JPEGs at PIL's default quality 75 with 4:2:0 subsampling**
  despite a comment claiming it does not. On rock that throws away exactly the high-frequency
  contrast that shows cracks. Monkey-patch `Image.Image.save` to force quality 95, subsampling 0
  (3.17 → 9.92 MiB of texture for the same pixel count).
- It also embeds PNG unless you hand it a JPEG round-tripped through `BytesIO`, and omits normals
  unless you pass `include_normals=True`.
- **GitHub rejects any file over 100 MiB and Pages does not resolve LFS pointers**, so the web model
  is fitted to a 92 MiB budget. An oversized blob also survives in local history — `git reset
  --soft origin/main` before re-committing.

## The viewer (`v2/index.html`)

- **Camera framing must account for aspect ratio.** Distance from `max(size.x, size.y)` alone
  leaves the model tiny in a wide window. Use
  `1.12 * max(size.y/2/halfV, size.x/2/(aspect*halfV))`. This was got wrong twice.
- The reconstruction's world is **y-down** (`camera.up.set(0, -1, 0)`), so the largest `y` is the
  bottom of a route.
- `LineBasicMaterial.linewidth` is ignored in WebGL on almost every platform. Use
  `Line2` + `LineGeometry` + `LineMaterial`, and update `resolution` on resize.
- **Two coincident fat lines z-fight**, which chops the coloured line into dashes wherever the
  outline shows through. `polygonOffset` is not a fix — the depth error grows as you zoom in and the
  dashes come back. Scale the outline group about the camera each frame instead
  (`scale = 1+eps`, `position = -camera.position * eps`): every point moves straight away from the
  eye, so the screen position is untouched and there is real world distance between the strokes.
  Cap `eps * distance` below the clearance the line was lifted by, or the outline sinks into the rock.
- Pages **gzips the GLB**, so `ProgressEvent.total` is the compressed size while `loaded` counts
  decompressed bytes and the bar overshoots. Hardcode the real sizes.
- Labels are a 2D canvas overlay, not sprites, so their boxes can be measured against each other.
  Keep the overlay `pointer-events: none` and hit-test clicks against last frame's boxes on the
  renderer's canvas, with a "pointer barely moved" guard — otherwise every orbit ending on a label
  navigates away.

## Metadata, not models

Bolts and routes are separate JSON files the viewer overlays. `korno_v2.glb` and
`korno_v2_light.glb` have not changed since they were built, and should not — verify with
`git rev-parse HEAD:v2/korno_v2.glb 4218f66:v2/korno_v2.glb`.

- **Multi-view agreement beats any confidence threshold.** The bolt detector is out of its training
  domain on drone frames (bolts 12–34 px instead of 30–100, median score 0.30). Keep every
  detection, ray-cast it, cluster in 3D, and ask whether several independent photos put a bolt in
  the same place. 94 of 113 candidates were seen once and dropped; the 19 survivors agree to within
  0.001–0.028 across up to 7 views and form two plausible vertical lines.
- openclimbing paths are `x,y|x,y|…` normalised to the photo. A **trailing letter on `y` is the
  point type** (`A` anchor, `B` bolt, `P` piton, `S` sling, `U` unfinished) and a trailing colon
  means the segment to the next point is dotted. Reading them as plain floats fails.
- Grades are keyed on UIAA in `gradeColors` (openclimbing's `gradeData.ts`). The ramp is flat within
  a tier, so `parseInt` on the leading number reproduces the whole table exactly — verified against
  14 grades including `7+/8-`, `9+/10-` and `10-`.
- A route drawn with 2–6 points must be **resampled before ray-casting**. The points land on the
  rock correctly; it is the chords between them that cut through bulges — up to 94 cm here.
  Resample, lift along the mesh normal, verify each point by casting back from the camera, then
  simplify with a tolerance *below* the lift so the remaining chords cannot eat through it.

## The blurry band above h ≈ 1.55

Parts of `korno_v2.glb` are photo-sharp and parts are smeared, with a false "edge" running the
length of the wall between them. Measured, not guessed:

| | |
|---|---|
| dense point spacing below the line | 0.0029 units |
| dense point spacing above it | 0.011 units (~16× fewer points per area) |
| texel size at 8192 × 4500 | 0.00184 units |
| camera heights | last row at h = 1.32–1.85, **nothing between 1.85 and 2.38** |
| planar-UV stretch | 17 % of triangles > 45°, 4 % > 60° |

**Why.** The drone never flew above the top of the wall, so the upper band is only ever seen at a
grazing angle from far away. Dense stereo needs a patch to be visible and well-textured in several
views to accept a depth; up there it accepts far fewer, and `stereo_fusion --min_num_pixels 4`
draws a hard line exactly at the coverage boundary — that is the "edge", it is a data boundary, not
geometry.

The blur itself is a **texturing** problem, not a resolution problem. The texture is baked from the
*colours of the dense points* (KD-tree inverse-distance interpolation). Below the line the points
are closer together than one texel, so every texel gets its own measurement and the texture is as
sharp as the photo. Above it one measurement is spread over ~6 texels, so the bake is interpolating
mush no matter how large the texture is. The planar UV projection makes it worse on steep faces,
where a square of texture is stretched over a much larger square of rock.

**How to fix it, in order of payoff.**

1. **Texture from the photos instead of from the point cloud.** This is the big one and it does not
   need a new flight. `mvs-texturing` (`texrecon`) or OpenMVS `TextureMesh` both take COLMAP output
   directly: for each triangle they pick the best-viewing photo and sample the original 8000 × 4500
   pixels, with seam levelling and global colour adjustment. Texture detail then depends on what the
   photos saw, not on how many depth points survived fusion — so the upper band comes back to roughly
   photo resolution even though its *geometry* stays coarse. Expect a CPU kernel of an hour or two.
2. **Real UV unwrap** (xatlas) instead of the planar projection, so steep faces stop being stretched
   and the texture budget is spent evenly. Worth doing at the same time as (1).
3. **Lower `--min_num_pixels` to 2–3 for the upper band** (or run fusion twice and merge). More
   points up there, at the cost of more noise — this softens the false edge but does not make the
   texture sharp on its own.
4. **More photos.** The only fix for the *geometry* above h ≈ 1.85 is a flight that actually looks
   at it — a higher pass, or an orbit with the camera tilted up. Nothing in post can invent
   measurements that were never taken.

Note that (1) alone should remove almost all of the visible complaint: the smudged look is the bake,
and the bake is fixable from data already on disk.
